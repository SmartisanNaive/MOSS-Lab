# Xiaozhi MCP bridge

English | [中文](README.zh.md)

The local MOSS launch configuration mounts this Cordis plugin alongside the existing Web Agent. When `XIAOZHI_WSS_URL` is set, it opens one outbound secure WebSocket and exposes MCP tools. The address is a credential and is never logged. Without an endpoint the authenticated local workbench remains available. The socket reconnects with capped exponential backoff and WebSocket ping/pong checks. Reconnection re-registers tools without resubmitting accepted Agent turns; job receipts remain in memory only.

Voice delegation uses the `moss-experiment` preset named **实验助手**, with a laboratory persona and the experiment tools, including `request_experiment_input` for missing essential conditions. It does not mount the coding preset, shell, or repository-engineering instructions.

`moss_delegate(message, newExperiment=false)` forwards the user's words to the active experiment conversation. Supplementary conditions and parameter changes reuse that conversation; only an explicit new experiment creates another. Do not supply a session ID from the model. The deployment can choose an initial session with `sessionId`, otherwise the first request creates one in the existing workspace, or in the configured `workspacePath` when no workspace exists. The private `bindingPath` file records the active identity and navigation sequence using an atomic replacement. A subsequent message after restart uses that identity; a missing conversation or a saved coding preset is reported rather than silently replaced. Explicitly start a new experiment to adopt the experiment preset while preserving the old conversation.

`moss_task_status(jobId, userQuery=false)` observes the accepted turn. `completed` means the Agent replied, including a clarification question; it never means a robot experiment completed. A new amendment immediately supersedes the previous voice intent and steers the same conversation. Unclaimed obsolete voice inputs are removed, and obsolete analysis cannot publish a passed check or preview. A timeout or ambiguous submission stays observable. Shutdown stops observation, not the Agent. Job receipts remain memory-only. Workflows started from the Web UI in the bound conversation publish their checked preview through the same workbench. Such a view has `jobId=null`; earlier MCP job receipts remain unchanged. Publication carries its captured owner, so a late result cannot overwrite a newer voice intent.

`moss_experiment_status(id)` reads the active delegated conversation, falling back to the configured initial session before delegation. `moss_status` reports the computer-side service, delegation availability and supported experiment tasks, not hardware readiness. No robot execution tool is exposed by this bridge.

The same authenticated Connection carrier serves `GET /api/xiaozhi-workbench` with the latest navigation sequence, session, job, status and result, plus credential-free `connection` and `wakeup` diagnostics. `connection.status=ready` means the endpoint requested and received the tool list, not that a physical microphone has been tested. The Web client follows `focusSequence` only on first opening, a request for essential conditions, or the current checked preview becoming ready. Ordinary amendments and status polls preserve the user's selection. Old previews stay hidden while a replacement is prepared; the exact current checked revision can appear before the Agent finishes its reply. `POST /api/xiaozhi-workbench/message` accepts JSON `{message, newExperiment?}` as a local text fallback through the same delegation service; a same-origin Origin header is required, and arbitrary session identities are rejected. It does not grant additional Agent permissions.

This is a single-operator deployment. The Xiaozhi endpoint does not provide a verified human identity; its holder can submit work with the Web Agent's existing local permissions. Session ownership checks are not user authentication. The deployer must keep the endpoint private and avoid duplicate bridge instances.

Speech decisions limit automatic waiting acknowledgements to three per task cycle at offsets 0, 15 and 45 seconds; early completion does not fill the remaining slots. Amendments share the budget, while a new task after a terminal reply resets it. After the limit, tool responses explicitly request silence. Completion reserves one short sentence; explicit user progress questions are separate. The hosted model still controls actual speech, so device testing is required. Completion is delivered through task-status queries in an active voice dialog; no idle-device speech channel is provided.

Run focused checks from the project root with Node 24.9 or later:

```sh
node --import tsx/esm --test internal/xiaozhi/*.test.mjs
```

Hardware microphone recognition and hosted tool selection must be tested by speaking to the physical device. A received `connection.lastCall.source=xiaozhi-mcp` distinguishes endpoint traffic from the local HTTP fallback. Configured `diagnosticsPath` records connection transitions and tool names, without endpoint tokens or user message bodies. Local HTTP/MCP injection and browser checks do not establish microphone behavior or robot readiness.

On macOS, the first accepted delegation opens the workbench when `MOSS_AUTO_WAKE=1` (the default). `MOSS_BROWSER_APP` selects Google Chrome (default), Microsoft Edge or Safari. The service reuses a tab with the same local origin, restores a minimized window, and opens a new window when no matching tab remains. The first wake after a service restart authenticates the tab; later ordinary amendments only check that a tab exists without foregrounding or reloading it. A missing tab is reopened. Clarification and current-preview-ready events restore and foreground the window. macOS may require the operator to allow browser automation. Login URLs travel to the native helper over stdin rather than command arguments or logs. A failed or disabled wake does not cancel the accepted task; its status and reason remain in `wakeup`, and a failure is also logged without credentials. Other operating systems report `unsupported_platform` when wakeup is enabled; use the open Web page or disable wakeup there.

The deployment config controls `transport.reconnectMinMs`, `reconnectMaxMs`, `connectTimeoutMs` and `heartbeatMs`, `feedback.offsetsMs` and `pollWaitMs`, and `wakeup.enabled`, `browserApp` and `timeoutMs`. These affect connection supervision and the trusted local browser helper, not the Agent tool permissions.
